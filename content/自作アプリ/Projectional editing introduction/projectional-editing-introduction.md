# 構文エラーのない世界へ — Projectional Editing と Incremental Computation が拓くエディタの未来

## はじめに

プログラマーなら誰でも経験がある。括弧を一つ閉じ忘れて画面が真っ赤になる。セミコロンが一つ足りなくてビルドが通らない。考えている途中なのに、エディタは容赦なく「構文エラー」と叫ぶ。

この問題には構造的な原因がある。**テキストエディタはプログラムを「文字の並び」として扱う**からだ。プログラムは本来、変数の束縛や関数の適用といった構造を持つ木（AST: Abstract Syntax Tree）だが、プログラマーはそれを文字列に「エンコード」して書き、コンパイラがそれを毎回「デコード」（パース）し直す。このエンコード/デコードの往復の中で、途中状態の文字列は構造として意味をなさない瞬間がどうしても生まれる。

もしプログラムの構造そのものを直接編集できたら？ 構文エラーという概念自体が存在しない世界を作れたら？

この問いに答えるのが **Projectional Editing** であり、その実用的な課題を解決する鍵が **Incremental Computation** にある。本記事では、この二つの概念を結びつけ、次世代のプログラミング環境がどのような姿になるかを紹介する。

---

## 1. Projectional Editing とは何か

### テキストエディタの裏側

従来のプログラミングでは、以下の流れでコードが処理される。

```
プログラマー → テキスト入力 → パーサー → AST → コンパイラ → 実行
```

プログラマーが書くのはテキスト。パーサーがそれを構造（AST）に変換する。このモデルでは、パーサーが心臓部だ。パーサーが理解できない文字列を書いた瞬間、すべてが止まる。型チェックも、補完候補も、リファクタリングも、パーサーが成功しない限り何も動かない。

### AST を直接編集する

Projectional Editing はこの構造を根本から変える。

```
プログラマー → AST を直接操作 → 射影（Projection） → 画面に表示
```

プログラムの「本体」はテキストではなく AST そのものだ。画面に表示されるテキスト的な見た目は、AST を人間向けに「射影」（プロジェクション）した結果にすぎない。同じ AST を、テキスト風に表示することも、ブロック図として表示することも、数式として表示することもできる。

この発想の最大の利点は、**構文エラーが原理的に発生しない**ことだ。AST は常に木構造として整合しているから、「括弧の閉じ忘れ」に相当する状態がそもそも存在しない。

### 「穴」（Hole）という概念

では「まだ書き終わっていない部分」はどう表現するのか。Projectional Editing では **穴（Hole）** を使う。

```
let x = _ in _
```

この `_` が穴だ。「ここにはまだ式が入っていないが、式が来るべき場所だ」と型システムに伝えている。穴があるプログラムも、穴がないプログラムも、同じように型チェックでき、場合によっては実行すらできる。ミシガン大学の Hazel というプロジェクトは、この「穴のあるプログラムにも意味を与える」という考え方を形式的に証明している（Omar et al., POPL 2017; POPL 2019）。

## 2. Projectional Editing の良さ

### 2.1 構文エラーからの解放

最も直接的なメリット。AST を直接編集する以上、「パースできない状態」が存在しない。初学者がプログラミングを学ぶとき、構文エラーの解読に費やす時間は膨大だ。Projectional Editing はその負担を根本から取り除く。

### 2.2 複数の表現を自由に切り替え

同じプログラムを複数の方法で表示・編集できる。

- **テキスト表現**: 従来のコードの見た目
- **ブロック表現**: Scratchのようなビジュアルプログラミング
- **数式表現**: 数学的な式を自然な記法で
- **図表表現**: 行列やグラフをそのまま表示

JetBrains社の MPS (Meta Programming System) はこの考えを実用化した代表的なシステムで、mbeddr という組み込みC言語の拡張環境では、状態遷移図やデシジョンテーブルをコードと同じファイル内に直接埋め込める。

### 2.3 言語合成が容易

従来、二つの言語を混ぜて使うとパーサー同士が衝突する（文法の曖昧性）。Projectional Editing では AST を直接扱うのでパーサーがなく、異なる DSL（ドメイン特化言語）を自由に組み合わせられる。

### 2.4 リアルタイムの型情報

穴のあるプログラムにも型がつくため、編集のどの瞬間でも型情報が利用可能。「この穴には Int 型の式を入れてください」「この穴に入れた式は期待される型と矛盾しています」といったフィードバックが途切れない。

---

## 3. Projectional Editing の難点

### 3.1 Viscosity（粘性）問題

Voelter et al. (FSE 2016) による実測研究で確認された本質的な問題。**簡単な変更に多くのステップが必要になる。**

テキストエディタでは `1 + 2` を `(1 + 2) * 3` に変更するのは直感的だ。括弧を打って末尾に `* 3` を足すだけ。

Projectional Editor では同じ変更に、まず `+` ノードを選択し、「式で包む」アクションを実行し、`*` 演算子を選び、右辺に `3` を入力する。操作の粒度が AST ノード単位なので、テキスト的な直感と噛み合わない場面が多い。

### 3.2 テキスト入力の自然さの喪失

プログラミングにおいて「テキストを打ち込む」行為は、思考をそのまま流し込むプロセスだ。

```
"えーと、ここに関数を..."  → fn 入力開始
"あ、やっぱり let 束縛"    → BS → let 入力
"名前は... x"             → let x
"型注釈つけたい"           → let x :   ← ここで型を考える
"Int で"                  → let x : Int =
"値は..."                 → 考え中...
```

各ステップで文字列は「パースできない状態」を経由するが、これはバグではなく**自然な思考のリズム**だ。

Pure Projectional Editor ではこれが「穴をクリック → 値を入力 → 次の穴をクリック」というフォームの穴埋め作業になる。思考とアクションの対応関係が崩れ、「流れるように書く」感覚が失われる。

### 3.3 「壊してから直す」リファクタリングの困難

ベテランプログラマーは頻繁に「一旦コードを壊してから直す」。関数の構造をまるごと書き換えたいとき、テキストエディタなら不完全な状態を恐れずに大胆に編集できる。Pure Projectional Editor では AST が常に整合していなければならないため、このスタイルの編集に大きな制約がかかる。

### 3.4 外部ツールとの非互換

git diff、grep、vim といったテキストベースのツールチェインが使えない。プログラマーの既存のワークフローとの断絶は、採用の大きな障壁になる。

---

## 4. Hazel の解決策: Gradual Structure Editing

ミシガン大学の Hazel プロジェクトは、上記の問題に正面から取り組んでいる。彼らが提唱する **Gradual Structure Editing**（段階的構造編集）は、テキスト的な入力の自然さと構造的な保証を両立させるアプローチだ（Moon, Blinn, Omar, VL/HCC 2023）。

鍵となるアイデアは「テキスト入力は許すが、AST が壊れることは許さない」という妥協点にある。

- テキストを打ち込める。`let x = 1 + ` のような途中状態も許容される。
- しかし内部的には、この途中状態は「未完成の式を含む穴」として AST 内に保持される。
- 入力が完全な式として解釈可能になった瞬間、自動的に AST ノードに「昇格」する。

つまり、パーサーの役割は「テキスト全体を AST に変換する心臓部」から、「テキスト入力を AST 操作に翻訳するアダプタ」へと変わる。

```
【従来のパーサー】
テキスト（完全なプログラム）→ AST
失敗: 全く意味のない状態

【新しい役割: Text Input Adapter】
テキスト入力の断片 → AST 操作の列
失敗: 穴を挿入して AST は常に整合
```

さらに、Grove（POPL 2025）は Projectional Editing を複数人の同時編集に拡張する CmRDT（可換CRDT）を定義している。異なるプロジェクション（テキスト/ビジュアル）を使う複数のユーザーが同じプログラムを同時に編集し、自動的に収束することが証明されている。

## 5. ここで問題になるのが「計算コスト」

Gradual Structure Editing の仕組みを理解すると、一つの疑問が浮かぶ。

**文字を一つ打つたびに、AST 全体の型チェックをやり直すのか？**

答えがイエスなら、大規模なプログラムでは実用に耐えない。エディタの応答性はミリ秒単位で問われる。キーを打つたびに数百ミリ秒の遅延が生じたら、誰も使わないだろう。

ここで **Incremental Computation**（インクリメンタル計算）が登場する。

---

## 6. Incremental Computation とは何か

### 6.1 本質: 前回の結果を再利用する

Liu (2023, Foundations and Trends in Programming Languages) はインクリメンタル計算の本質を次のように定式化している。

> プログラム f と入力変更操作 ⊕ が与えられたとき、
> f のインクリメンタル版 f' とは以下を満たすもの:
>
> **f(x) = r ならば f'(x, y, r) = f(x ⊕ y)**
>
> f(x) の結果 r を再利用して、変更後の f(x ⊕ y) を効率的に計算する。

これは**微分の離散版**だ。連続関数の微分が「入力の微小な変化に対する出力の変化率」を求めるように、インクリメンタル化は「入力の離散的な変更に対する出力の効率的な再計算」を求める。

### 6.2 身近な例

最も単純な例。1 から n までの合計を計算する関数 `sum(n)` がある。

```
sum(100) = 5050   ← これは計算済み
sum(101) = ?      ← 1 から 101 までを全部足し直す必要はない
sum(101) = sum(100) + 101 = 5151   ← 前回の結果を再利用
```

これがインクリメンタル化だ。`sum' = λ(n, r). r + (n + 1)` が `sum` のインクリメンタル版。入力の変更 ⊕ は `n + 1`、前回の結果 r を使って O(1) で計算できる。

### 6.3 III メソッド: 体系的なインクリメンタル化

Liu はインクリメンタル化を体系的に行うための **III (Iterate-Incrementalize-Implement)** メソッドを提案している。

| ステップ | 内容 |
|---------|------|
| **I1. Iterate** | 最小の増分を決定し、繰り返し適用して目的出力に到達する方法を定める |
| **I2. Incrementalize** | 各反復において、保持した補助値を使って高コストな操作をインクリメンタルにする |
| **I3. Implement** | 保持する値を効率的に格納・アクセスするデータ構造を設計する |

重要な洞察は、**プログラムが使う抽象のレベルによって、必要なステップが異なる**ということだ。

| プログラムの特徴 | 高レベル抽象 | 必要なステップ |
|------------|----------|------------|
| ループと配列 | なし | I2 のみ |
| 集合式（DB クエリ等） | データ抽象 | I2, I3 |
| 再帰関数 | 制御抽象 | I1, I2 |
| 論理規則 | データ + 制御 | I1, I2, I3 |

そして Liu が繰り返し強調するのは、**高レベルの抽象を使うほど、インクリメンタル化は容易かつ強力になる**ということだ。

## 7. Projectional Editor に Incremental Computation を適用する

### 7.1 エディタのパイプライン

Gradual Projectional Editor の内部は、関数の連鎖（パイプライン）として理解できる。

```
文字入力 → Text Input Adapter → AST操作 → Groveグラフ → AST(穴付き)
    → 型チェック(Marking) → MarkedAST → テキスト表示
                                       → ビジュアル表示
```

各段階が関数だ。

| 関数 | 入力 | 出力 |
|------|------|------|
| `translate` | テキスト編集 | AST操作列 |
| `decompose` | グラフ | 穴付きAST |
| `mark` | AST + 型コンテキスト | 型注釈付きAST |
| `project_text` | 型注釈付きAST | テキスト表示 |
| `project_visual` | 型注釈付きAST | ビジュアル表示 |

### 7.2 各関数をインクリメンタル化する

文字を一つ打つたびにパイプライン全体を再実行するのは無駄だ。変更は局所的なのだから、**変更の影響を受ける部分だけ再計算すればよい**。

これが Liu のインクリメンタル化の直接適用だ。各関数 f に対して:

```
f(ast) = result
f'(ast, 変更, result) = f(変更後のast)
```

#### 型チェック（Marking）のインクリメンタル化

型チェックは AST 上の再帰関数だ。III メソッドでは:

- **I1 (Iterate):** 最小増分は AST ノード 1 つの変更。型チェックの再帰構造から、変更されたノードから根に向かうパス上のノードだけを再計算すればよい。
- **I2 (Incrementalize):** 各ノードの型判定結果をキャッシュし、変更されていないサブツリーの結果を再利用する。

1万ノードの AST で 1 つのノードを変更した場合、全体を再計算すると O(10000) だが、インクリメンタル版は変更されたノードから根までの O(log n) 〜 O(depth) だけで済む。

Hazel プロジェクト自体も OOPSLA 2025 で "Incremental Bidirectional Typing via Order Maintenance" という論文を発表しており、まさにこの問題に取り組んでいる。

#### テキスト表示（Projection）のインクリメンタル化

テキスト表示も AST 上の再帰関数だ。変更されたノードの表示だけを更新すればよい。具体的には **Rope** というデータ構造（文字列の平衡二分木）を使い、局所的な文字列の挿入・削除を O(log n) で処理する。

#### グラフ操作（Grove）のインクリメンタル化

Grove のグラフは辺と頂点の集合だ。集合操作に対するインクリメンタル化は、Liu の用語では **有限差分法 (finite differencing)** に相当する。例えば「辺を一つ追加したとき、AST のどの部分が変わるか」は、HashMap を使って O(1) で特定できる。

### 7.3 Chain Rule: パイプライン全体のインクリメンタル化

個々の関数のインクリメンタル版を得たら、それを合成する必要がある。Liu はこれを微積分の **連鎖律 (chain rule)** の離散版と位置づけている。

```
パイプライン全体の更新:

1. AST操作をグラフに適用       → グラフのどこが変わったか（Δgraph）
2. decompose'(Δgraph)         → AST のどこが変わったか（Δexpr）
3. mark'(Δexpr)               → 型注釈のどこが変わったか（Δmarked）
4. project_text'(Δmarked)     → テキスト表示のどこが変わったか（Δtext）
```

各段階の「出力の変更」が次の段階の「入力の変更操作」になる。これにより、文字を一つ打つたびに走る処理は、パイプライン全体ではなく**変更が波及する部分のみ**に限定される。

## 8. なぜこの組み合わせが重要なのか

Projectional Editing 単体では、概念は美しいが実用上の壁（粘性、自然さの喪失）がある。Incremental Computation 単体では、汎用的な最適化手法ではあるが、それだけでは何を作るかが定まらない。

両者を組み合わせると、以下が実現する。

**構文エラーのない世界 + リアルタイムの応答性**

- 穴を使った AST により、プログラムは常に整合 → 型情報が途切れない
- Gradual Structure Editing により、テキスト入力の自然さを維持 → 粘性を軽減
- Incremental Computation により、局所的な変更は局所的に処理 → ミリ秒の応答
- CmRDT (Grove) により、複数人が異なる表現から同時編集 → 自動収束

さらに Liu が強調する **「高レベル抽象ほどインクリメンタル化が容易」** という原則は、エディタの実装言語選択にも影響を与える。代数的データ型やパターンマッチングを持つ言語（ML 系、Haskell、MoonBit 等）で AST を定義すれば、再帰関数の構造が明確になり、III メソッドの I1（最小増分の決定）が容易になる。集合を第一級のデータ構造として扱える言語なら、I2（有限差分法）が体系的に適用できる。

## 10. これから

未解決の課題は多い。

- **Text Input Adapter の設計**: テキスト入力を AST 操作に自然に変換する仕組みは、最も難しい問題の一つ。`1 + 2` のあとに `*` を打つと、AST の構造が大きく変わる（`+` ノードが `*` ノードの子に移動する）。こうした「テキストでは1文字の変更が、木構造では大規模な組み替え」となるケースをどう扱うか。
- **DSL からの自動導出**: 特定の言語だけでなく、任意の DSL に対してエディタの各コンポーネント（パーサー、型検査、表示、編集操作）を自動生成できるか。Liu の部分評価との関係でいえば、これは Futamura の射影に対応する問題だ。
- **分散環境での整合性**: CmRDT による同時編集はオフラインでも機能するが、大規模なチームでの実用には更なる検証が必要。

しかし、方向性は明確だ。**プログラムを文字列ではなく構造として扱い、その構造の変更を効率的に伝播させる。** この二つの原理の組み合わせが、次世代のプログラミング環境の基盤になる。
